# 反馈分类标准

## 一、目标

分类标准用于把不同来源、不同语言和不同长度的玩家评论，转换为可比较的结构化字段，并让每一条标签能够通过关键词、规则和人工抽检追查到依据。

## 二、字段定义

| 字段 | 含义 |
|---|---|
| `feedback_id` | 分析结果的稳定编号。 |
| `source` | 评论来源平台。 |
| `source_url` | 可公开访问的来源页面。 |
| `collected_at` | 采集时间。 |
| `published_at` | 评论公开时间。 |
| `language` | 平台语言或标准化语言代码。 |
| `content` | 去除 HTML 和异常空白后的评论正文。 |
| `anonymized_author` | 基于平台作者标识生成的不可逆短哈希。 |
| `rating` | Steam 推荐状态或商店星级评分。 |
| `theme` | 单一主主题。 |
| `sentiment` | 正向、负向、混合、中性。 |
| `severity` | 低、中、高、严重。 |
| `suggested_action` | 可直接进入运营看板的动作建议。 |
| `human_theme` | 人工抽检主题。 |
| `human_sentiment` | 人工抽检情绪。 |
| `human_severity` | 人工抽检严重度。 |
| `is_correct` | 人工抽检三项是否全部与自动分类一致。 |
| `notes` | 自动分类命中词。 |
| `theme_confidence` | 主题规则置信度，取低、中、高。 |

## 三、主题标准

1. **性能与优化**：卡顿、掉帧、闪退、崩溃、加载、下载、更新体积、内存、网络和阻断型 Bug。
2. **外挂与安全**：外挂、透视、自瞄、作弊、护航、卖挂、反作弊和举报不处置。
3. **匹配与队友**：匹配池、单排、组队、人机、排位、挂机、抢包、摆烂和队友差异。
4. **武器与干员平衡**：武器、干员、后坐力、伤害、削弱、加强、超模和强度争议。
5. **搜打撤与经济**：爆率、物价、物资、交易行、收益、撤离、保险和经济回收。
6. **地图与模式**：地图结构、点位、复活、载具、模式轮换和玩法机制。
7. **付费与通行证**：价格、皮肤、通行证、抽奖、礼包、返场和付费价值。
8. **任务与成长**：任务、活动、等级、奖励、解锁、新手引导、成长节奏和肝度。
9. **客服与封禁**：误封、封禁、观察期、黑屋、申诉、客服、账号异常和注销。
10. **界面与操作体验**：界面、准星、按键、设置、交互、音效、语音、字幕和视觉反馈。
11. **正向反馈**：明确肯定、推荐、喜欢、期待和具体称赞，且没有需要归入主问题主题的明确投诉。
12. **其他**：语义不足、纯情绪、跨语言无效文本，或暂时无法可靠归因的内容。

## 四、多主题处理

评论出现多个问题时，按以下顺序确定主主题：

1. 阻断使用、账号安全和大范围信任问题优先。
2. 外挂、误封、闪退、无法登录优先于一般体验建议。
3. 如果同权重，选择关键词命中更强、描述更具体的主题。
4. 长评中既有优缺点时，不强行把正向词覆盖问题主题；情绪可标为混合。
5. `notes` 保留全部命中词，方便复核是否漏掉次要问题。

## 五、情绪标准

- **正向**：明确肯定、推荐，或评分较高且没有显著负面表达。
- **负向**：明确批评、拒绝推荐、失望、愤怒，或低评分且没有具体肯定。
- **混合**：同一评论中同时存在真实优点和明确问题。
- **中性**：陈述信息、提问、寻找组队，或语义不足以判断情绪。

规则会同时参考评分和文本。评分只作为方向信号，不覆盖明确的反讽或复杂复合表达。

## 六、严重度标准

- **低**：建议、疑问、轻度体验差异、正向反馈。
- **中**：影响体验但不完全阻断，例如爆率、匹配、平衡、任务和 UI 问题。
- **高**：明显影响持续游玩，例如严重卡顿、频繁崩溃、外挂较多、封禁争议和客服不处理。
- **严重**：无法登录、持续闪退、账号暂停、误封未解、文件损坏重复发生或安全环境全面恶化。

严重度不是问题发生概率，也不是全量玩家规模，只表示该条公开反馈的上行影响和运营紧迫性。

## 七、去重与脱敏

- 去重键：来源 + 匿名作者 + 规范化正文。
- 规范化仅用于去重，不修改原始正文。
- 用户名、头像和主页不进入清洗数据。
- 作者标识使用 SHA-256 短哈希，不能直接还原平台账号。
- 看板展示时进一步隐藏链接、攻击性词汇和过长正文。

## 八、质量门槛

- 所有来源必须记录采集时间和限制。
- 人工抽检不得只看自动标签，必须阅读原文。
- 任何概率、封禁、作弊规模或满意度结论都必须另行验证。
- 规则更新后必须重新运行处理、看板和报告，保证数字一致。
